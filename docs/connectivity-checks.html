CONNECTIVITY / INTERPRETATION

What the connectivity checks are designed to tell you

LANVEXA is designed to bring basic Windows Ethernet observations into one first-pass sequence. Each check answers a narrow question; none proves overall network health or a root cause.

SEMANTICS STILL UNDER VERIFICATION

Exact targets, timeouts, resolver behavior, success conditions, and error handling have not yet been verified from the desktop application. They must be published before controlled distribution.

Addressing

Designed to show whether the selected wired interface has usable addressing information. The exact criteria for “usable,” including IPv4 and IPv6 handling, remain unverified.

Gateway

Designed to evaluate a configured gateway check. A failure should be read only as that check not meeting its success condition; the transport, target selection, timeout, and policy implications remain unverified.

DNS

Designed to evaluate a configured DNS check. The queried hostname, resolver selection, cache effects, address-family behavior, timeout, and precise success condition remain unverified.

Configured TCP connectivity

Designed to evaluate a configured TCP/443 connection. The target, timeout, address-family behavior, and precise success condition remain unverified. A result should not be generalized beyond that configured connection.

Read the sequence without inventing a cause

  • PASS means the configured check met its success condition.
  • FAIL means it did not meet that condition.
  • NOT TESTED means it was not run or could not appropriately proceed.

Use the combined observations to decide what to investigate next. For example, a DNS failure can focus the next investigation on name resolution, but it does not by itself prove which DNS component or policy caused the failure.

Before controlled distribution

LANVEXA must publish the actual input, target, timeout, success condition, failure condition, not-tested condition, and error behavior for each shipped check.
